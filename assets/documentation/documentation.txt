CHAPTER I: Overview of the Project
--------------------------------------------------------------------------------

In the second and third decades of the 21st century, we are seeing an increasing
amount of hidden surveillance and spying on everyday people, unbeknownst to them
on apps such as Facebook and Instagram by governments and intelligence agencies.
Mobile smartphones have even been reported to quietly listen in on what you say
in real life, by people who start seeing advertisements for what they've just
talked about. There is colossal hidden surveillance on all regular people.

As of 2026, most people are not aware of this and how dangerous it is in the
context of living a free life. This project aims to be a strong pillar of rescue
from the governments and companies spying on us every day, by providing a
completely private and secure method of communicating with your friends by means
of cryptography. It's not intended for mass use, but rather for isolated cases
when a group of people really do need to have an online conversation in secret.

For instance, if a company trade secret must be protected from spying mobile
phones and everyday chat apps, whoever is having a conversation involving that
secret can talk on this system and be assured that nobody - be it a company or a
government entity - will ever find out. Not only are your messages encrypted and
authenticated, only visible to your friends on the system, what's more - your
internet service provider can't even find out WHO you talked to, since all your
outgoing network traffic is first routed to the system's relay server before
reaching your friends' devices. The server operator CANNOT decrypt and read
people's messages, only intended recipient users can do that.

Secretly talking to your friends on Rosetta is ideally bootstrapped by starting
with an off-system meeting agreeing a time for the first secret session on the
system, the chat room name, its owner (who creates it) and the code name of each
friend participating in the chat. Then, future secret meetings can be planned on
the system directly. Everybody picks a new codename before entering a chat room,
there's no visible identity for anybody.

The system must run on a secure GNU/Linux machine, not Windows, MacOs or the
like, as these spy on people to begin with and your messages are likely to leak,
especially if you are already a person of interest who's being actively tracked.
A relatively modern CPU supporting 256-bit vector SIMD instructions is required.
In the future, a custom handheld radio communicator will be devised as well.

Another goal this project has had right from the start is to get me better at C
programming and good modern software engineering practices for large projects,
a resounding success. I've learnt enormous amounts from it, having written over
10 thousand lines of C code for it. Not only C programming, it's also taught me
how to keep a large software project healthy and advanced performance analysis
and optimizations techniques based on CPU microarchitecture & compiler behavior.

The server's public key comes readily available to clients at install time.

The programming interfaces provided to access all supported physical methods of
communication (e.g. the Linux Sockets API for TCP provided by the OS itself)
are all abstracted away into a unified API that the system can always work with.

This unified communications interface consists of 4 function pointers to the 4
basic communication operations - begin session, end session, send message and
receive message. Regardless of the internals of each physical communication
method and its own programming interface, Rosetta's communication machinery will
wrap its interface into this unified API, to make it seamlessly accessible for
the whole system where communication behaviour and code is present. This allows
new methods of communication to be easily integrated into the system.

A Test Framework was developed for the Rosetta. It simulates real human users by
spawning local OS processes and having them talk using local interprocess
communication sockets (AF_UNIX on GNU/Linux). It drives the exact same code
paths as real human users, while saving headaches caused by things like changing
IP addresses and firewall rules getting in the way.

The Test Framework supports both manual testing, where multiple virtual users
can be spawned and the test operator sends messages from each one by hand,
observing in real time how they get delivered to the intended recipient virtual
users, as well as fully automated test simulations where virtual users get
spawned and send each other messages programmatically based on a schedule.
Multiple chat rooms, each with different guest virtual users, can be present
at once during testing, to observe how well the system maintains them.

CHAPTER II: Custom underlying libraries
--------------------------------------------------------------------------------

Two underlying libraries have been developed for the system - one for doing math
on gargantuan numbers efficiently and one that contains implementations of all
the cryptography algorithms needed for the system's security.

1. Big Integer Library
======================

The custom BigInt library provides mathematical operations on unsigned integers
of huge sizes. Modern cryptography requires operations on numbers with thousands
of digits, so this was a mandatory requirement. This library is what makes it
possible to perform critical and parameterized cryptographic operations.

A big integer is represented as an object of a C struct called bigint. It holds
the bare minimum needed to maintain an evolving big integer - its maximum size,
its current size, both in bits, and a pointer to its heap-allocated bits buffer.
A constructor-like function is used to initialize a bigint object of that struct
to a given integer. A destructor-like function cleans a bigint's resources up.

Saving a big integer to a file and loading one from a file is also supported.

A common term used in big integer libraries is "a limb". This is simply a part
of a number. For example, a 325-bit integer has 10 32-bit limbs and a final part
of size 5 bits. We have 16-bit limbs, 32-bit limbs, etc. Different algorithms
in the library use different limb sizes, but that's all there is to it.

Big integers are always stored in little-endian byte order by the library.

Operations currently implemented in the library:

Nullifying, equating, saving to and loading from a file, comparison, addition,
subtraction, multiply, divide, powering, simple modular multiplication,
Montgomery Modular Multiplication & Powering, Rabin-Miller primality test, and
utility functions for debugging like a pretty printer for a bigint's bits and
switching the endianness of a bit string.

Addition, subtraction and multiplication are currently implemented to operate on
32-bit limbs at a time, while division operates on 16-bit limbs, as that allows
the algorithm to rely onl on 64-bit storage throughout its operation. Algorithms
for these 4 operations were taken from Handbook of Applied Cryptography.

Montgomery Modular Multiplication operates on 64-bit limbs. One peculiarity of
its implementation is that it currently hardcodes the parameters that depend on
the modulus M, that is: L (number of 8-byte limbs in M) and the multiplicative
inverse MU. This is acceptable in the context of Rosetta, since M stays constant
in the long run, and so do L and MU. It does mean, however, that should a new
modulus M be decided later on, L and MU have to be either changed, or finally
implemented as input arguments, though that might slow things down a little.

A special Dual Montgomery Modular Powering function takes the arguments for two
function calls to the standard montgomery modular powering and performs special
interleaved montgomery modular multiplication on both operand sets at once where
possible. Namely, in the Montgomery Modular Powering algorithm, we go over the
bits of the power and: do one montgomery multiplication for sure, and do one
further montgomery multiplication if the current bit of the power is set. The
interleaved Montgomery Powering performs interleaved montgomery multiplication
acting on both input operand sets for the first multiplication, and also does it
for the 2nd multiplication if both powers' bit at that index happen to be set.

This was done as a successful optimization acting on performance profiling data
that indicated Montgomery Modular Multiplication to be accounting for 61% of all
CPU cycles with under-utilized CPU micro-op execution ports. It resulted in a
10% speed up.

A further neat optimization to Montgomery Modular Multiplication came as a
reaction to the GCC compiler emitting a vectorized and a non-vectorized version
of the inner loop, due to pointer aliasing concerns. I factored this inner loop
out into its own function, which I can pass __restrict__ pointers to, in order
to guarantee to the compiler that the pointers won't be used for overlapping
memory operations. This resulted in the compiler successfully dropping the
slower non-vectorized version of the inner loop altogether and only emitting the
good vectorized version of the loop.

2. Cryptography algorithms library
==================================

This library is a collection of cryptography algorithms that are all used in the
system at various points in the security scheme. The implementations are mostly
taken from the algorithms' original RFC specifications.

Algorithm{X}(y, z) notation: This simply means we are telling the algorithm to
give us X bytes of output, and it takes y and z as input arguments. An example
of an algorithm with a custom output size is Blake2b.

Algorithms implemented as part of the library:

ChaCha20, BLAKE2b, one-pass Argon2id, Schnorr Signature generation & validation,
generation of a pseudorandom private key from /dev/urandom and its corresponding
public key, and a function to check a public key's form for integrity.

Some other notable cryptography algorithms are small enough and/or are used in
few enough places, that their code simply appears directly where they're needed,
instead of having their own function in the cryptography library itself.
Examples are HMAC and obtaining a Diffie-Hellman shared secret.

Currently, Argon2id only works with one pass, which is sufficient for security.

The RFCs that the implementation of various algorithms is taken from:

ChaCha20 - RFC 8439
BLAKE2b  - RFC 7693
Argon2id - RFC 9106
HMAC     - NIST.FIPS.198-1

For the other algorithms:

- Diffie-Hellman modulus M and prime factor Q: M is a ≈ 3070-bit prime positive
  integer and Q is a ≈ 320-bit prime positive integer exactly dividing (M - 1).
  The bit width of these two can vary, that is just what the system uses now.

- Diffie-Hellman generator is given by the formula: G = [2^ ((M - 1) / Q)] mod M

- Generating a private key is simply grabbing pseudorandom bytes from a source
  that is deemed adequate from a security standpoint, in this case from the
  standard /dev/urandom file on GNU/Linux. Generating a 320-bit private key
  simply means grabbing 320 bits from that pseudorandom source and setting the
  highest bit to 1, to make sure it really is 320-bit.

- Generating a public key "A", from a private key "a", is done with the formula:
  A = G^a mod M

- Computing a shared secret on multiple sides.

  In order for Alice and Bob, both in possession of the same Diffie-Hellman M, Q
  and G, to generate the same shared secret "X" on both sides, given Bob's
  private/public keys (b, B) and Alice's pair (a, A) and Bob holding Alice's
  public key, while Alice holds Bob's public key:

    Bob's shared secret: X = A^b mod M
  Alice's shared secret: X = B^a mod M

  Of course, their public keys must have been computed with the same M, Q and G.

- Generating and validating a Schnorr Signature for authentication:

Let:

(a, A) - Alice's private/public key pair;
     M - the diffie-hellman modulus;
     Q - the prime number that exactly divides (M - 1);
     G - the diffie-hellman generator;

1. Call BLAKE2B{64} with input - whatever we're signing.
   The produced 64-byte hash of this is called the prehash PH.

2. Call BLAKE2B{64} with input - the signer's private key concatenated with the
   prehash, reduce the result of this modulo (Q - 1), add 1. Yields secret k:

   k = [BLAKE2B{64}(a||PH) mod (Q - 1)] + 1

3. Compute R = G^k mod M
4. Compute e = BLAKE2B{64}(R||PH), truncated to bitwidth of Q.
5. Compute s = ( k + ((Q - a) × e) ) mod Q

The signature itself is (s, e).
--------------------------------------------------------------------------------
To validate against public key A and whatever was signed, the receiver:

1. checks that 0 <= s < Q, and that e has the expected bitwidth (that of Q).
2. Computes the prehash PH as in step 1 for signature generation.
3. Computes R = (G^s * A^e) mod M. This is: [(G^s mod M) * (A^e mod M)] mod M
4. Computes val_e = BLAKE2B{64}(R||PH), truncated to bitwidth of Q.

   Check that val_e is equal to e. If it is, validation passes.
   Under any other circumstances, signature validation fails.
--------------------------------------------------------------------------------

CHAPTER III: The Rosetta client
--------------------------------------------------------------------------------

4. Overview of the client
=========================

The client is what users run in order to use Rosetta. It has both a graphical
user interface (GUI), made using wxWidgets in C++, and a terminal user interface
(TUI) made in C like the rest of the project.

Different usecases necessitate different ways of using the system, which is
achieved using different Client Driver Programs, which differ in some ways at
the highest level of abstraction,  while still using the same core functionality
of the client layer.

Client code used by real human users in the base system lives under /src/client/
while the TUI-based client driver is currently part of the Test Framework.

The design of the client allows different ways of using Rosetta. The 4 primary
parts of the client layer are:

- Client User Interface
- Client Primary Functions
- Client Packet Functions
- Client Communications

The user interface part implements the mechanism via which the user of the
system will be creating rooms, talking to their friends, etc. It is separated
from the Primary Functions part on purpose, so that different ways of using the
system can be created by having different UI implementations, which are called
client driver programs, described in the next chapter.

The primary functions part contains abstractions for the main client-facing
operations that can be performed as part of using Rosetta: register, login,
create chatroom, join chatroom, send message, leave chatroom, logout. They
handle logic such as sanitizing user input for codename and their password and
calling, and handling any arising errors from the appropriate lower-level
functions for payload construction/parsing and functions for communication,
strictly using the Unified Communication Interface, which is what the
Communications Machinery component exposes to the rest of the system, so it can
elegantly use the same communication functions regardless of which underlying
physical communication mechanism is currently being used.

The packet functions part contains functions that construct payload buffers for
outgoing packets to the server and functions for processing incoming packets
from the server. Each recognized payload structure has its own unique magic
constant that identifies it, right at the start of the payload buffer. After
constructing/parsing a payload buffer, this part of the client layer does not
itself invoke functions that execute communication operations, this is done one
abstraction layer up, inside the Primary Functions part.

The client communications part (conceptually residing in the Communications
Machinery component in the system design) of the client layer is what actually
contains the implementations of the functions that the function pointers in the
Unified Communication Interface are set to during initialization. This part
contains implementations of every possible function that these function pointers
can be set to. For instance, the transmit_payload() function in the Unified
Communication Interface can be set to a payload sending function for AF_UNIX
(local interprocess communications) to talk to other local processes, which is
what the Test Framework does, or it can be set to an AF_INET payload sending
function that uses Internet Sockets in the Linux Sockets API to undertake TCP
communications between human users. Both of these concrete communication
functions are implemented in the client communications part of the client layer.

5. Client driver programs
=========================

Client driver programs implement the Client User Interface part of the client
layer in different ways. Each client driver program runs the exact same
code paths for the client primary functions and client packet functions parts of
the client layer. They may be using the same, or different communication
functions in the client communications part, which is invisible to the higher
levels of abstraction in the client layer, including to the UI part, since these
parts only utilize functions provided by the Unified Communication Interface:
transmit_payload, receive_payload, end_communication, init_communication.

There are currently 2 client driver programs: The wxWidgets GUI based one that
human users utilize, and the terminal interface one used in the Test Framework.

One important distinction between the 2 is the way in which the running client
is notified of a received message by the polling thread. In the former, we have
to actually change GUI elements, in the latter it's just printf(). In the
latter, when a client is notified that the chatroom they were in has been closed
by the owner of the room, a potentially blocked scanf() call has to be unblocked
as well.

This is done with conditional compilation using #ifdef. The GUI client driver
program defines the preprocessor macro USE_WX_GUI. Then, code that needs to
handle these events differently for different client driver programs uses #ifdef
and #ifndef to select the respective code for handling the events.

Here is some code in Client Primary Functions that illustrates this:

--------------------------------------------------------------------------------
Example 1:
---------

////////// Remove the wxWidgets GUI elements for being in a chat room if the
////////// client receives information that the room owner has closed the room:
////////// This does not have to be done for the terminal user interface driver
////////// program because there are no GUI widgets like buttons to remove.

#ifdef USE_WX_GUI
force_user_out_of_room();
#endif
--------------------------------------------------------------------------------
Example 2:
---------

////////// If not using the wxWidgets GUI client driver program, simply display
////////// the received message using printf(). Otherwise, call the appropriate
////////// message displaying function through a function pointer that had been
////////// been set during client initialization. In the wxWidgets GUI case, it
////////// will change the GUI element to have the received message displayed.

        own_ix, text_message_line);
#else

#endif

////////// display_received_msg function pointer will have been set to this
////////// function for the client driver program that uses the wxWidgets GUI:

/* Update GUI using the g_instance global pointer.
 *
 * Client polled the server and received a new message from somebody in their
 * chatroom. Display it on the user's chat room GUI window.
 */
void display_gui_message(char* message_line)
{
    wxString msg_to_display = wxString::FromUTF8(message_line);
    g_instance->GetEventHandler()->CallAfter([msg_to_display]()
    {
        g_instance->msg_entries->AppendText(msg_to_display);
        g_instance->msg_entries->AppendText("\n");
    });
    return;
}
--------------------------------------------------------------------------------

More than these 2 client driver programs can be implemented in the future.
The infrastructure and logical separation in the system design are already
there, making this an easy task.

6. Client workflow & payload structures
=======================================

Client workflow of each Rosetta user (be that a human, a bot, or other entities,
for example military drones coordinating with a central command base) is
as follows:

1. Upon installing Rosetta, create a local user save file by registering. This
   save file contains items needed for preserving logical state that outlives
   chat room sessions.

   The save file has 4 items:

      - chacha20 nonce for decrypting the saved private key.
      - user's long-term private key in encrypted form.
      - user's long-term public key not encrypted.
      - 8-byte string - part of Argon2 parameter S, used when intaking the user
                        password that emits the secret chacha20 key used to
                        decrypt the user's stored encrypted private key.

   TODO ITEM:
   For human-facing usage, this user file is simply created wherever the Linux
   working directory from which the user had started their Rosetta client was.
   Thus, it's important the user start the client from this working directory
   every time. This should probably be changed so that the user save file is
   always in a well known directory. This is a TODO item.

   TODO ITEM:
   Recent security analysis suggests this file will also contain saved chacha20
   counters the user has with each person they've met and talked to in the past,
   because currently this counter starts at 0 each time the user meets the same
   friend in a chat room, leading to a nonce reuse in chacha20, something that
   is not permitted by the security scheme. This is a TODO item.

   TODO ITEM:
   Mitigation measures in case this file is corrupted must be invented to harden
   the security of the system. This is a TODO item.

2. Each time the user wants to use Rosetta, the user logs in. The save file
   gets opened and parsed at this stage.

   This triggers a secure login handshake protocol with the server. A short-term
   pair of public and private keys is generated on the client and on the server
   side. They get a short-term DH shared secret with them. The client then
   encrypts the user's long-term public key and sends it to the server, which
   decrypts it. The message that sends the short-term public key in the clear
   is authenticated using HMAC, while communication afterwards is authenticated
   using Schnorr Signatures as per usual. The short-term key pair and shared
   secret are destroyed (zeroed out) as soon as the user's long-term public key
   is successfully decrypted on the server side and a session-length DH shared
   secret is established on both sides. Clients already have the server's long
   term public key at install time.

3. Now that the user is logged in, they are presented with the options to create
   a chat room, join one, or log out.

4. Creating a chat room makes this user the owner of the room. If that user
   leaves the room, it gets closed and everyone gets booted from it instantly.
   The user picks a new codename they should go by in that chat room.

5. Joining a chat room happens only if the user knows the name of a chat room
   and the time it will be open in advance. Existing chat room names are not
   shown anywhere, they are hidden and secret, only the intended participants
   know about their existence, which means they must have a pre-made schedule
   that dictates when their chat rooms will be opened and what codename each
   intended guest will go by during their stay in the chat room. It's possible
   to leave a chat room and rejoin using a different codename, in case someone
   joined with the wrong codename.

6. Sending a message to everyone currently in the chat room involves generating
   a new pseudorandom key to be used to encrypt only that one message. This key
   is itself encrypted using a session-length key, extracted from the DH shared
   secret that the user maintains with everybody else in the chat room.

   It follows that each message is protected by not one, but two secret keys.

   The server cannot decrypt and see messages, only clients in the chat room
   can. The server simply relays it to the proper clients and only those that
   are in the same chat room.

   Each receiver client is assured that the message was not edited en route by
   an eavesdropper and that it really was sent by the legitimate sender and
   relayed by the legitimate server by means of two Schnorr Signatures attached
   to the payload containing the message - one signature generated by the
   sending user and one generated by the server before relaying the message to
   the receivers in the chat room.

7. Leaving a chat room as a non-owner brings back the options to join a chat
   room, create a new one or log out. Again, leaving a chat room as the owner
   (you had created chat room in the first place) kicks out everyone from it.

8. Logging out closes Rosetta. Long-term user artifacts remain in the save file.

In order for the client and the server to talk to each other, a payload protocol
is defined. It is a set of known legitimate payload structures, each with its
own PACKET_ID magic constant defined in src/lib/rosetta-helpers.h, giving an
initial shield against unrecognized (possibly malicious) transmissions.

The moment a transmission is received by the server or by the client, they first
check this PACKET_ID field at the start of each payload. If it's not one of the
legitimate recognized ones, the transmission is immediately and silently dropped
in order to not inform a potential attacker of it.

All existing legitimate payloads are given as a comment before the functions
that implement their generation and parsing in client-packet-functions.h and in
server-packet-functions.h because a significant naming convention rework is
currently planned, due to a confusion that arises by the fact that the same
PACKET_ID is given to 2 different payloads (both on the server side and on the
client side) where the distinction is that the payload is being received or is
being generated.

After the payload naming convention rework is completed, all legitimate payload
structures will be given and well documented in here.

CHAPTER IV: The Rosetta server
--------------------------------------------------------------------------------

8. Overview of the server
=========================

The Rosetta server is an executable that's deployed and runs on AWS currently.
It sits between all Rosetta clients, which never send transmissions to each
other directly, but rather rely on the server as a relay mechanism. This means
that the server disallows users' Internet Service Provider (ISP) from finding
out not only what they're saying, but also WHO they're talking to, despite
seeing the target IP addresses in their network traffic, complementing secrecy.

It has several important responsibilities:

    - Securely relay a sender's message to everyone they're in a chatroom with.
    - Maintain critical state about chatrooms and their participants.
    - Gracefully handle unexpected situations, e.g. a user losing connection.
    - Securely work with sensitive cryptographic artifacts.
    - Maintain a secure environment, protect itself & users from eavesdroppers.

The server has 4 primary components:

    - Top-level operator : Communication API selection, listening loop, etc.
    - Primary Functions  : Transmission processing, server initialization, etc.
    - Packet Functions   : Payload crafting & parsing.
    - Communications     : Unified Communication Interface server side logic.


9. Server workflow & payload structures
=======================================

The top-level operator begins by checking the command line arguments and based
on those, selects the chosen underlying communication interface. After that, it
calls the server initialization function. If all is good so far, it enters the
infinite listening loop that waits for new connection requests and onboards new
clients upon receiving one.

Currently, the server architecture is such that a new thread is started for each
client, but that will probably be optimized to only start a new thread when the
current number of threads can't handle all the incoming polling requests of
currently connected clients.

The server's long-term public key is already present with clients at install
time. Clients wishing to connect and use Rosetta first send a short-term key
pair, as does the server. Then a short-term DH shared secret is computed on
both sides. Authentication until that point, before Schnorr Signatures can be
computed, is done with HMAC. This short-term shared secret is used to transport
the client's long-term public key to the server in encrypted form, which means
it gets destroyed almost instantly after it's created.

Then the server handles requests for users to create a new chat room, join an
existing one, leave a chat room or send a message in their current chat room.
When a client sends a message, the server can't decrypt it, it merely relays the
message to everyone else who is in the same chat room as the sender, while
attaching its own Schnorr Signature to the payload, so the receiver(s) can be
assured that the message really was relayed by the legitimate Rosetta server.

The server's biggest workload and time eater is Schnorr Signatures. Verifying
them and computing its own. This is why, in bigint.h, the Montgomery Modular
Multiplication and Powering functions were optimized to such a big extent. Since
each client polls the server multiple times per second, it's predictable and
computable how many clients the server can handle at once before the total time
it takes the server to process all signatures overtakes the time between poll
requests of a client, which is currently every set to 100,000 microseconds, aka
100 milliseconds, aka 0.1 seconds. This means the server has 100 milliseconds
to process the poll requests of EACH connected client in total. Currently, the
time it takes to verify a poll request's incoming signature is, on average, a
little over 4200 microseconds, or 4.2 milliseconds. 100 milliseconds of client
poll interval gives the server enough time to handle about 20 clients per thread
if a future redesign allows multiple clients being processed by 1 thread, unlike
the design now, where each client makes a new thread start.

As mentioned in the part of this documentation that talks about the Client
component of Rosetta, in 6. Client workflow & payload structures, the system
uses a custom payload protocol that describes how each recognized payload buffer
will look like exactly. The server uses this as much as the client does. It
parses payloads constructed by clients and generates payloads that clients will
be parsing, according to this payload protocol. Diagrams of each recognized
payload can be found in server-packet-functions.h, the protocol itself has some
minor shortcomings, a fix for which would have me change many places of how
it would be documented here, which is the reason I will only document this
payload protocol once the rework effort which fixes these shortcomings is done.
The payload diagrams in server-packet-functions.h (and client-packet-functions.h
for that matter) will have to suffice for the time being.

10. Server deployment strategy
==============================

The server is currently deployed on an AWS EC2 Linux machine. This necessitates
that each client's public IP address must be whitelisted on the AWS panel, in
order for the client's requests to be able to reach the server. This becomes
especially annoying if a client's public IP address gets changed frequently by
their ISP. Currently, clients' IP addresses get added manually to the AWS
whitelist menu for the AWS machine's NIC, but I believe this can be automated.

Perhaps the handling of changed clients' IP addresses can be automated in the
future too, by a small system that checks if the IP address of a client is still
the same as registered for access to the Rosetta server, or perhaps some AWS
machinery that automatically and securely whitelists Rosetta users somehow.

The server's IP address is given in a #define in the client software currently,
which will have to be improved and possibly automated in the future.
Specifically, it is #defined in client-communications.h. The server does not
need client IP addresses, since it never initiates a connection with a client,
only clients initiate communication with the server once a user logs in.

In either case, Rosetta is not intended for mass use, but rather for small
groups of people who really want to talk in secret online. I will definitely
know about every user, so it's not really a problem to whitelist their IP
addresses on AWS for the time being.

CHAPTER V: Communication Machinery
--------------------------------------------------------------------------------

Rosetta's system design is set up in a way that allows multiple underlying
communication mechanisms to exist and be used for different usecases of the
system and allows new communication mechanisms to be easily integrated.

This chapter describes how that is achieved.

12. The Rosetta Unified Communication Interface
===============================================

When any part of the system needs to perform a communication operation, such as
sending a message, it does so through an abstract function interface that is
always the same regardless of what the underlying communication mechanism
currently being used is.

That interface consists of 4 function pointers, both on server and on client
side, which describe in an abstract way the common communication operations that
are actually being carried out.

For the client, these 4 communication operations are:

    - Initialize communication: Establish a connection with the Rosetta server.
    - Send a message: Server receives it and relays it to the user's friends.
    - Receive a message: Waits for the server to send a reply to a request.
    - End communication: Disconnect from the server.

Corresponding 4 function pointers, in client-primary-functions.h:

uint8_t (*init_communication) (void);
uint8_t (*transmit_payload)   (uint8_t* buf, size_t send_siz);
uint8_t (*receive_payload)    (uint8_t* buf, uint64_t* recv_len);
void    (*end_communication)  (void);

For the server, these 4 communication operations are:

    - Initialize communication: Start-up and enter onboarding new clients loop.
    - Send a message: Send a reply to a client request.
    - Receive a message: Receive a request from a client.
    - Onboard new client: Sits and listens for new client connection requests.

Corresponding 4 function pointers, in rosetta-server.c:

uint8_t(*init_communication)(void);
uint8_t(*transmit_payload)  (uint64_t socket_ix, uint8_t* buf, size_t send_siz);
ssize_t(*receive_payload)   (uint64_t socket_ix, uint8_t* buf, size_t max_siz);
uint8_t(*onboard_new_client)(void);

Every underlying communication mechanism exposes its own usage interface.
Rosetta shouldn't and doesn't need to concern itself with the communication
interface of every single underlying communication mechanism that has been
intergrated into the system. This is why the Unified Communication Interface,
consisthing of these 4 function pointers, was created.

Both the Server and the Client have a communication source code file which
contains the actual implementations of how the communication mechanism-specific
usage interfaces are wrapped by logic that ultimately allows these interfaces to
be used through the 4 function pointers in the Unified Communication Interface
and allows Rosetta to undertake communication operations through that unified
interface, regardless of what underlying communication mechanism is being used.

The whole system uses the Unified Communication Interface in every single place
where one of the 4 main communication operations must be carried out.

The logical connection between the Unified Communication Interface and the
interface exposed by the actual underlying communication mechanism happens by
setting the 4 function pointers to the 4 wrapper functions that deal with the
specific communication mechanism's usage interface. Remember, a set of 4 wrapper
functions for each integrated communication mechanism is present in the server's
and client's respective communications source code file. This function pointer
assignment happens at system initialization time, for both server and client.

13. Supported underlying communication mechanisms
=================================================

Currently there are 2 underlying communication mechanisms integrated: Internet
communications over TCP sockets on Linux, for the real human user-oriented use
case of the system, and local interprocess communications over AF_UNIX sockets
on Linux, for the Rosetta Test Framework use case.

Here is the communication mechanism selection code for the server:

/* Select local interprocess communications with AF_UNIX sockets. Used by the
 * Rosetta Test Framework when simulatig human users via local OS processes.
 */
#define SELECT_LOCAL_UNIX_COMMUNICATIONS          \
    init_communication = ipc_init_communication;  \
    transmit_payload   = ipc_transmit_payload;    \
    receive_payload    = ipc_receive_payload;     \
    onboard_new_client = ipc_onboard_new_client;

/* Select internet communications over TCP. Used by the regular user-facing
 * version of the system.
 */
#define SELECT_TCP_INTERNET_COMMUNICATIONS        \
    init_communication = tcp_init_communication;  \
    transmit_payload   = tcp_transmit_payload;    \
    receive_payload    = tcp_receive_payload;     \
    onboard_new_client = tcp_onboard_new_client;

To avoid confusion, I will repeat: The actual implementations of each set of 4
wrapper functions that connects the Unified Communication Interface to the
usage API of each possible communication mechanisms live in the server's and
client's communication source code file:

 - Server implementations: src/server/server-communications.h
 - Client implementations: src/client/core-client-layer/client-communications.h

Then, the point in the source code where the Unified Communication Interface is
initialized to one of the integrated underlying communication mechanisms' usage
API is simply an invocation of one of these macros, enabling the system to use
the underlying communication mechanism through the 4 function pointers in the
Unified Communication Interface elegantly.

The code for the client side is analogous: A macro with a set of 4 function
pointer assignments for each integrated communication mechanism and then an
invocation of one of the macros depending on which mechanism is selected for the
particular use case.

In the future, if a new underlying communication mechanism is to be added and
integrated into Rosetta, nothing about how the system carries out communication
operations will change at all. There would simply have to be a new set of 4
wrapper functions added in the client's and server's communication source code
file that wrap around the API that the new communication mechanism itself
exposes to the world.

One idea that keeps coming up for a future communication mechanism is radio.
That would allow, for instance, drones or robots containing small embedded chips
to use Rosetta for encrypted and authenticated communication, for instance in a
military use case.
