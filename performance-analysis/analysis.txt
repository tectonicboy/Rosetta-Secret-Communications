TITLE: Improving the use of CPU micro-op execution ports via code interleaving.

BACKGROUND.

Modern desktop x86_64 CPUs break down assembly instructions into smaller
units of work called micro-operations (uOPs). The work represented by them
is carried out by a number of execution ports. The hardware micro-architecture
is such that these execution ports can be fed several micro-ops in the same
CPU cycle and they all operate independently of each other, meaning they can
all be utilized in parallel. In reality, however, it's often not the case.

This is called instruction-level parallelism (ILP) and achieving a high degree
of it leads to better, more optimized software that runs faster. ILP can be
hindered by a number of things, such as inappropriate memory access patterns
and dependency chains in the incoming assembly instructions, where instruction
X+1 must wait for the one before it, instruction X, to produce its result so
that X+1 can use it in its own operands. This obviously prohibits parallel
execution of several micro-ops by several execution units at once. One remedy
of this is interleaving independent work in the code where such dependency
chains are present, so the CPU execution ports can find parallel work instead
of waiting with mostly idle ports for the dependency to be resolved.

The effects of this are amplified by the fact that the micro-architecture allows
the CPU to look at a whole window of instructions and execute independent ones
out of order, preserving correctness by "officially" finishing them in order,
which is ensured by an internal hardware structure called the Reorder Buffer.
This is called out-of-order execution. Thus, even if the independent interleaved
instructions don't exactly come one after another, the CPU can still find said
independent work and keep the execution ports busier, which is what we want.

In this report, I present my efforts of applying such code interleaving to
mitigate a state of under-utilized micro-op execution ports due to dependencies
in the compiler-emitted assembly code of one of my Big Integer operations in C
and achieving a 10% speed up. I talk about how this optimization is explained
from a CPU micro-architectural point of view and show the tools that I used to
carry out the performance analysis - Top-down microarchitecture analysis, the
Perf tool, flame graphs and LLVM Machine Code Analyzer.

PART I.
Introduction.

While analyzing the performance of my side project's communication server on
GNU/Linux using Top-down microarchitecture analysis methodology, I saw that the
Core-Bound metric (a sub-bucket of Backend-bound) was consistently being
reported to be nearly 10%.

I obtained this using the Perf tool:

sudo perf stat --topdown -- bin/rosetta-server
sudo perf stat -M tma_core_bound,tma_memory_bound -- bin/rosetta-server
sudo perf stat -M tma_ports_utilization -- bin/rosetta-server

To find out which function was contributing the most to this, I used:

sudo perf record -e cpu_core/exe_activity.1_ports_util/ -g -- bin/rosetta-server
sudo perf report

This tells Perf to take a call graph snapshot every time the CPU spends X cycles
being mostly idle (only 1 execution port is being utilized to work on a uOP).

This reported that 61% of cycles in which the pipeline was stalled due to poor
execution port utilization in the CPU backend (only 1 port is utilized) was
attributed to my Montgomery Modular Multiplication function, montgomery_mul(),
under the "self" column.

This is also the function that takes up the most time of anything else in the
running communication server, an insight obtained by looking at which functions
appeared in the largest number of Perf snapshots when simply counting down
regular CPU cycles between each taken snapshot:

sudo perf record -e cpu_core/cycles/P -g -- bin/rosetta-server

Emitting an SVG flamegraph from this, to render in a web browser:

sudo perf script | stackcollapse-perf.pl | flamegraph.pl > my-flamegraph.svg

Emitting a terminal-friendly render of the same information, but in descending
order of functions that were at the top of the call graph in the largest number
of Perf snapshots, so we can see the actual function body code that is taking
the longest time in the continuously running communication server:

sudo perf report --sort overhead,symbol --stdio

Now, the communication server has to validate a cryptographic signature on each
payload it receives, which involves the following modular powering calculation:

R1 = (G^s) mod M
R2 = (A^e) mod M

G, A and M are 3072-bit unsigned Big Integers (implemented by myself in C),
while the powers e and s are 320-bit, so this is nothing short of a gargantuan
calculation. The server has to perform it all the time, as each connected
client sends poll requests 10 times per second, each of which contain a
signature that must be validated by the server. Even if using epoll() instead
of the clients manually polling the server, a point at which the server has to
deal with validating many signatures in a very short window of time will
eventually be reached when enough clients connect to the server at once.

The montgomery powering code spends most of its time in montgomery_mul() calls,
so I directed my focus to montgomery multiplication and the way I implement it.

Closing in on various parts of that function by surrounding the call site itself
and then each part of the function's own code with clock_gettime() and seeing
which part accounts for the largest percentage of the function's latency, I
concluded that the vast majority of montgomery_mul()'s own work is, in turn,
done in the following inner loop:

static inline
__attribute__((always_inline))
void mont_mul_inner_loop(      uint64_t* const __restrict__ R_limbs,
                         const uint64_t* const __restrict__ N_limbs,
                         const uint64_t* const __restrict__ X_limbs,
                         const uint64_t* const __restrict__ Y_limbs,
                         const uint64_t i,
                         const unsigned long long q)
{
    uint8_t C;
    uint8_t D;
    unsigned long long  Ul;
    unsigned long long  Uh;
    unsigned long long  Vl;
    unsigned long long  Vh;
    unsigned long long  W;

    /* T, a 3-limb variable, resides in R->bits buffer for optimization:
     * T = (unsigned long long*)(R->bits + ((MONT_L + 1) * MONT_LIMB_SIZ));
     */
    #define T  ( (unsigned long long*)(R_limbs + (MONT_L + 1)) )
    for(u64 j = 1; j < MONT_L; ++j){
        Ul   = _mulx_u64(q, N_limbs[j], &Uh);
        Vl   = _mulx_u64(Y_limbs[i], X_limbs[j], &Vh);
        C    = _addcarryx_u64((u8)0, Ul, R_limbs[j], &Ul);
        Uh  += (u64)C;
        D    = _addcarryx_u64((u8)0, Vl, T[1], &Vl);
        C    = _addcarryx_u64((u8)0, Ul, Vl, T);
        D    = _addcarryx_u64(D, Uh, Vh, &W);
        C    = _addcarryx_u64(C, W, T[2], T + 1);
        T[2] = (u64)C + (u64)D;
        R_limbs[j-1] = *T;
    }
    #undef T
}

The loop counter MONT_L is 48 when using 3072-bit montgomery modulus N,
which is what the system uses under real circumstances. Known at compile time
and always remains the same. It is a #define-d constant.

I had already factored this inner loop out into a function, so I could give the
compiler's memory aliasing analyzer clear hints that I guarantee the pointers
to the actual bits of the Big Integers (to their limbs, a limb being 64 bits)
are guaranteed to be the only methods used to access that memory buffer in
the pointer's lifetime, so the compiler can more aggressively optimize the loop
with its own optimization passes. Of course, this guarantee is true by design
in my system. I was not able to do this by simply opening a new local scope
with a { } block in montgomery_mul() and declaring the pointers as __restrict__
there. GCC seems to prefer this info be given to it on the function argument
level. I did this optimization separately from this interleaving effort here.

For the BigInt sizes I stated for G, A, M, s and e, the two Montgomery powering
calls run a combined total of 2,165,760 iterations of this inner loop. To keep
this as short as I can, I won't give detailed steps to parts I deem can be
taken for granted, like how I get this number of inner loop iterations here.

I theorized that the dependencies in Montgomery Multiplication itself could
be leading to under-utilizing the CPU backend's execution ports, despite the
Reservation Station having micro-ops ready to feed the ports, as these would
be waiting for their operands to be produced by earlier ones they depend on.

We can clearly see such a dependency here:

D = _addcarryx_u64((u8)0, Vl, T[1], &Vl);
C = _addcarryx_u64((u8)0, Ul, Vl, T);
D = _addcarryx_u64(D, Uh, Vh, &W);
C = _addcarryx_u64(C, W, T[2], T + 1);

The first call stores its result in Vl and any produced carry in D, then the
next call immediately uses Vl as input. The 4th call uses results produced by
the second and third calls (64-bit variable W and the carry C).

Therefore, I experimented with an interleaved version of Montgomery powering
that can process two independent powering streams in the same function and thus
get the chance to call an interleaved montgomery_mul that would operate on both
operand sets in the same function code, with the most impactful part of this
being the interleaved inner loop for the new dual_montgomery_mul(). I have
interleaved the code for the two independent multiplication streams in the
inner loop by simply doing an iteration on one operand set and then, before
going to the next iteration, doing the same steps for the second operand set.

In the end, it proved to be a significant performance win.

It decreased the time taken to perform these two montgomery modular powering
calculations by 10%. These two calculations are by far the largest part of
validating a signature, which, in turn, is what the communication server spends
the vast majority of its time doing. I explain exactly how I measure the average
latency that these two modular powering operations take in the next section.

Average latency BEFORE interleaving the two powering streams: 4703 microseconds
Average latency AFTER  interleaving the two powering streams: 4213 microseconds

This is all using my own C implementation, no project dependencies other than
the C standard library, syscalls and standard GCC compiler functionality.

Running on a 13th Gen Intel Core i7 CPU, singlethreaded, on a GNU/Linux system
locally installed, kernel 6.19, compiled by GCC 15.2.1 with -O3 -march=native.
Isolating the process to run on P-cores only with taskset had no effect on
neither latency measurements, nor the reported TMA metrics for P-cores.

PART II.
Measuring latency.

I surround the code I'm measuring (the 2 montgomery powering calls, or the one
interleaved powering call in the optimized case) with:

clock_gettime(CLOCK_MONOTONIC_RAW, ...)

Each latency reading is obtained from the difference of the two times. Since
each reading is upwards of 4000 microseconds, clock_gettime() is safe to use
here without itself messing with the measured latency readings, as this call is
implemented in modern GNU/Linux systems to simply read a piece of memory mapped
by the kernel for each process, readily available without switching to kernel
space at all, which means we obtain the current time in at most 1 microsecond
and, from my research on the Web, less than 100 nanoseconds nowadays.

Once I've collected 500 latency readings from the running communication server,
they get dumped to a file with fwrite(). A small python program then computes a
stabilized average latency from these 500 readings in the following way:

First, eliminate outliers:

1. Sort the latency readings in ascending order. Split into 2 halves.
2. middle-indexed reading of first half (median) = Q1. The 25th percentile.
3. middle-indexed reading of other half (median) = Q3. The 75th percentile.
4. Interquartile range IQR = Q3 - Q1.
5. LowerFence LF = Q1 - (1.5 * IQR).
6. UpperFence UF = Q3 + (1.5 * IQR).
7. Outliers are all readings LESS THAN LowerFence OR GREATER THAN UpperFence.

With the outliers gone, we take the average of the remaining readings.

Repeat this process of collecting batches of 500 latency readings, removing
outliers and noting their average (sum divided by count) 128 times. This gives
us tens of thousands of individual latency readings to work with.

With 128 stabilized averages, we compute the final average latency.

Using this method, I consistently get final averages within 2 microseconds of
the median final average. That is solid, given my 4000+ microsecond readings.

I have made sure to have enough individual latency readings, and that the
mechanism used to take each reading (clock_gettime() function) is fast enough
that it won't interfere with the profiling process in any meaningful way.

PART III.
Validating my hypothesis as to why we get this speed-up and explaining it from
a CPU micro-architecture point of view.

Interleaved version is 10% faster because the Reservation Station is now able
to feed the backend's execution ports micro-ops from instructions that belong
to the second stream of Montgomery multiplication, out of order, while waiting
on stream 1's dependencies to produce the operands of stalled uOPs in the RS.

In the non-interleaved version, the Reservation Station had instructions fed to
it by the CPU Frontend, but for some of them, it was not able to feed their
micro-ops to available idle execution ports because the instructions in the RS
had dependencies on (input operands produced by) ones that were already
currently running in the ports. In other words, I improved instruction-level
parallelism and made better use of the Out-of-Order capabilities of modern
CPU microarchitecture by moving the 2nd Montgomery Multiplication stream
to be interleaved with the code for the first, instead of one after another.

Interleaving two streams in one function does increase register pressure and
makes the compiler spill registers more often, but the hot inner loop is still
small enough that its micro-ops fit inside the micro-op cache in the frontend
and its data fits in L1d cache and these trips to L1d cache are masked by
out-of-order execution of the other multiplication stream's micro-ops.

The first dose of validation comes from comparing the profile given for each
version by the Top-down microarchitecture analysis methodology (TMA).

III.3. Conclusion of TMA profiles comparison.

When comparing Montgomery Multiplication's share of instructions during which
the entire running system was stalled due to under-utilized CPU execution ports
in the two versions, we have 61% for non-interleaved and 55% for interleaved.

Put simply, in the interleaved version, of all the cycles during which the
system was stalled due to under-utilized CPU execution ports, 55% were cycles
spent running Montgomery Multiplication. It is 61% for the non-interleaved
version.

Put even more simply - The interleaved version reduced the blame that Montgomery
Multiplication takes for contributing to the entire system's stalled CPU cycles
in that category (under-utilized micro-op execution ports). Makes sense, right?

Furthermore, when comparing the Level-1 and Level-2 TMA buckets of the two
versions to see their overall TMA profiles, we can see that the interleaved
version has a smaller Core_Bound metric and a larger Memory_Bound metric,
leading to an overall higher Backend-Bound bucket. This does not mean that
the system in the interleaved version is utilizing the CPU backend less
optimally. The 3% jump in the level-2 Memory-Bound bucket of Backend-Bound is
expected, due to the increase register spilling, as we have a basic block of
code that is much larger now for the compiler to juggle the few available
registers between. It means the entire system, all parts of it, are now having
a 13% share of cycles stalled due to sub-optimal usage of the CPU backend.
All other parts of the system contribute to this percentage. The aim was to
decrease the core_bound metric and make Montgomery Powering faster, which the
interleaved version did. TMA_ports_utilization was decreased, which is further
proof that the interleaved version ITSELF is utilizing the execution ports in
a more optimal way, which is why it's 10% faster.

In conclusion, it is safe to claim that TMA analysis of the two versions has
given us reason to believe that the interleaved version is faster because it
is utilizing the CPU backend, more specifically the micro-op execution ports,
more optimally than the non-interleaved version of the two powering calls.

This is just an initial, coarsely-grained insight. A detailed simulation of
the CPU micro-architecture pipeline while running the workload sheds more light
on the precise reason that the interleaved version runs faster. Read on.

In the two interleaved Montgomery powering calls, Montgomery multiplication
represents over 99% of the workload. The inner loop, whose source code was
displayed at the beginning of this report, is itself 99% of the workload of
Montgomery multiplication.

Thus, simulating the microarchitecture pipeline in LLVM Machine Code Analyzer to
repeatedly run the instructions of the inner loop of both versions of Montgomery
multiplication gave deeper, more fine-grained and revealing insights:

This observation validates my hypothesis - where the CPU backend's execution

III.5. Number of Assembly instructions occupying the CPU backend in parallel.

From the pipeline simulation Timeline view, I can see that the interleaved
version gets more instructions residing in the CPU backend at various stages
in their execution (waiting in the Reservation Station to be fed to execution
port(s), being executed in port(s), or waiting in the Reorder Buffer, with their
result visible to the pipeline, to be retired in-order). Taking the length in
cycles of one of the longest-residing instructions, I can see:

NOTE: Instructions per iteration start at index 0.

NOTE: The two instructions in both illustrations are cherry picked to show the
      the window with the highest number of instructions in both versions.

Interleaved version:

----------------------------------------------------------------------------
D===================eeeeeeeeeeeeER  mov qword ptr [rdx + 400], rsi
...parallel instructions...
                                 D=eE-------------------------R  cmp rax, 48
----------------------------------------------------------------------------

In the displayed timeline exerpt:

First: Iteration  9, instruction 30
Last : iteration 10, instruction 72

Instructions per loop iteration: 73  (0 to 72).

Doing the math, we reach the insight that 117 instructions are being processed
by the CPU backend in parallel, in the best case, for the interleaved version.

Non-interleaved version:

----------------------------------------------------------------------------
D==============eeeeeeeeeeeeER  mov qword ptr [rax + 400], rcx
...parallel instructions...
                            D======E------------------R  movzx  esi, sil
----------------------------------------------------------------------------

In the displayed timeline exerpt:

First: Iteration 21, instruction 31
Last : iteration 24, instruction 17

Instructions per loop iteration: 40  (0 to 39).

Thus, 108 instructions are being processed by the CPU backend in parallel,
again for the best case, in the non-interleaved version.

Timeline diagram context:

- Each character from D to R is one cycle. Time in cycles moves to the right.
- D: Instruction was given to the Reservation Station by the CPU Frontend.
- =: Instruction waits in RS, can't yet go to its required execution port(s).
- e: Instruction's micro-ops are being worked on by execution port(s).
- E: Instruction's result is ready and visible to the pipeline at this cycle.
- R: Instruction is retired in-order from the Reorder Buffer at this cycle.

As long as we stay within the limits of the Reorder Buffer's number of slots,
which we are here, this is a clear win for performance. It shows that the
interleaved version is better tapping into the benefits of the highly parallel,
out-of-order design of the microarchitecture of today's desktop CPUs. It clearly
indicates the backend's execution ports are in fact being better utilized and
kept non-idle for more cycles by the interleaved version, which was the
hypothesis as to why it's faster in the first place.

It's possible to reach a number of assembly instructions residing in the
backend in parallel that is too high. When the CPU Frontend wants to feed
the CPU Backend an instruction, that instruction needs:

- A free slot in the Reservation Station, to wait for its operands if needed.
- A free slot in the Reorder Buffer (ROB), so it can be retired in-order.

If either of these limits is hit, the CPU Frontend simply stops feeding
instructions to the CPU Backend, stalling the pipeline. In this particular
case here, we are far from reaching such a bottleneck for this inner loop.

In conclusion, what we've observed in the Timeline diagram is a clear win here.


III.6. Properties of the assembly instructions emitted by the compiler.

III.6.1. Total instructions emitted for the inner loop:

Non-interleaved: 40 instructions PER ITERATION, 2 work units = 80 instructions.
Interleaved  x2: 73 instructions PER ITERATION, 2 work units = 73 instructions.

Same amount of work in fewer assembly instructions. Definitely a win.

A unit of work here is having processed one 64-bit batch (limb) of a Big
Integer's bits in the montgomery modular multiplication algorithm.

III.6.2. Instructions reported to have a latency of 0 cycles.

Instructions that LLVM Machine Code Analyzer reports as having a latency of 0
cycles are not handled by execution ports in the CPU backend at all. Instead,
a simple mov instruction could be handled by the Register Renamer as simply
changing a pointer to point to a different entry on the physical register file,
which is larger than the 16 architectural general-purpose registers in x86-64.

Another way an instruction can have a latency of 0 is when it's subjected to
fusion with other instructions.

These instructions obviously alleviate pressure from the execution ports. Thus,
having more of them in a smaller region of assembly instructions that will be
executed by the pipeline is beneficial.

The simulation I ran in LLVM Machine Code Analyzer reports:

Non-interleaved: 2 instructions with a latency of 0 cycles PER ITERATION.
Interleaved  x2: 4 instructions with a latency of 0 cycles PER ITERATION.

This is because the code for one iteration in the non-interleaved version simply
appears as two duplicates in one iteration of the interleaved version. However,
the win here is that in the non-interleaved version, 4 such instructions appear
every 80 instructions, while in the interleaved version, 4 of them appear every
73 instructions.

The fact that in the interleaved version we've done 2 units of work in 73
instructions, of which 4 had a latency of 0, while the non-interleaved version
does 2 units of work in 80 instructions, 4 of which have a latency of 0, COULD
indicate that the CPU backend's ports are more alleviated per 2 units of work
in the interleaved version. This would require further and deeper analysis to be
confirmed with certainty, so I restrict myself to saying "COULD indicate" for
now, to keep this report and myself honest and transparent.


IV.
Report conclusion.

Interleaving two Montgomery powering (and thus, two multiplication) streams has
successfully resulted in a significant speedup when doing two Montgomery Power
operations back to back for signature validation in my communication server.

My hypothesis, based on CPU microarchitecture, as to why it's faster:

The ability of modern desktop CPUs to execute instructions out of order allowed
the CPU backend's execution ports to work on the micro-ops of instructions from
the second multiplication stream that's interleaved with the code of the first.
These same ports, that now found work to do, were sitting idle in the
non-interleaved version, despite the Reservation Station having instructions
ready for them, because the only instructions available for them had input
operands that were produced by the ones that are currently being executed by
other ports. In simple terms, Out-of-Order execution is utilized better by
the interleaved version because, while stream 1's instructions are waiting on
dependencies, stream 2's instructions can begin execution out-of-order.

This was validated by LLVM Machine Code Analyzer running a detailed CPU pipeline
simulation, as well as by the Top-down microarchitecture analysis methodology.

V.
Future optimizations.

Currently, the compiler is spilling data from general-purpose registers to L1
data cache (conceptually, spilling them on the stack).

Investigate whether spilling them to vector registers would speed things up
even more. Be careful of which micro-op execution ports are used to handle
vector register to general purpose register moves, not to stall ports that are
already the most utilized.

This could speed the loop even more, especially in the interleaved version that
experiences heavier register spilling to the stack, because, given the right
circumstances (e.g. not using execution ports that already under heavy load),
reading values from the physical vector registers back into physical general
purpose registers can be faster than touching even L1 cache memory. In and of
itself, the fact that memory doesn't have to be touched at all can explain
such a speedup, if observed.

There are current efforts in LLVM and GCC to add optimization semantics
that will automatically spill to vector registers, but it's not there yet
from what I could gather.

Verify that the 11% core-bound L2 TMA bucket for original non-interleaved

Try the following optimization ideas for the interleaved Montgomery_MUL:

- Get rid of pointer to 3-limb variable T, as it's stored inside R's buffer.
Each active pointer consumes a register. x64 only has 16 of them.

- Don't pass N as an arg, as it's constant and the same for both MUL streams.

- Factor out inner loop into a function that takes ->bits pointers directly
as __restrict__ for both MUL streams, takes the two streams' q (1-limb var.
that remains constant for the inner loop) as const u64 arguments AND the

for stream 1 and then REUSING FOR STREAM 2 ANY REGISTER-SIZED TEMPORARIES
that do not matter for iteration I+1. These are at least the following:
Uh, Ul, Vh, Vl, carryC, carryD, W. Don't have a "version2" variable of them
for the 2nd MUL stream, simply reuse the same variables to perform iteration I
for the 2nd MUL stream too, as they are overwritten at the start of
iteration I+1 anyway.

IMPORTANT:

llvm-mca is a great tool for CPU pipeline simulation cycle by cycle. It stands
for LLVM Machine Code Analyzer. It takes an assembly code snippet and gives:

- How many execution ports the CPU backend has and which is used for what.
- which execution ports each instruction's micro-ops can go to;
- how many micro-ops each instruction is decomposed into;
- latency of each instruction;
- Reciprocal throughput of each instruction (RThroughput).
For example, Rthroughput = 0.20 means there are enough execution ports in the
CPU backend to be executing 5 of that instruction in parallel.
- Total cycles to run your assembly code. For all interations, if loop.
- Total number of instructions and uOPs executed. For all iterations, if loop.

 0      1     0.00                        mov   rdi, rdx

Here, we have instructions with 0 uOPs and instructions that take 0 cycles.
Explanation:

These are moves that were handled by the register renamer in the CPU frontend.
The CPU may only have 16 general purpose registers, but it has a much larger
physical file of actual hardware registers. This is how 2 instructions that
use RAX can run in parallel if the renamer assigns them different physical
registers in the register file. The Reservation Station (Scheduler) already
has info on which micro-ops need which physical registers in the file, this
is how it can feed the backend execution ports two instructions using RAX at
once. Then, because in the assembly code they were separate and came one
after another, this will be reflected in the Reorder Buffer (ROB) and this
hardware unit will make sure the instructions are RETIRED in proper order.

Another reason an assembly instruction can be shown to have 0 uOPs is because
the Decoder in the CPU Frontend fused it with the next instruction. Example:

[1]    [2]    [3]    [4]    [5]    [6]    Instructions:
 0      1     0.00                        add   rdi, 1
 1      1     0.20                        cmp   rdi, 48

Profiling harness automated to run Simulation 1 128 times for 128 averages.
Each average is made up of 500 completely organic calls of the montgomery
powering function over 30 seconds. The measurements.txt file shows each
stabilized average (from 500 calls) with outliers properly excluded via first
and third quartile statistical method:

1. Sort the data points in ascending order. Split into 2 halves.
2. middle-indexed value of first half (aka median) = Q1.
3. middle-indexed value of other half (aka median) = Q3.
4. Interquartile range IQR = Q3 - Q1.
5. Lower fence LF = Q1 - (1.5 * IQR).
6. Upper fence UF = Q3 + (1.5 * IQR).
7. Outliers are all data points X < LowerFence  OR  X > UpperFence.

Outliers are calculated for and removed from the 500 function call latencies
that were used to produce each of the 128 stabilized averages over 30 seconds.
Outliers are not removed from the 128 stabilized averages themselves. It takes
the automated latency measurement harness a little over 1 hour to collect all
128 stabilized averages and give the average for a SET.

Lastly, a final average is calculated of the 128 stabilized averages.
These are the results displayed here.

Each set takes ~ 1 hour to obtain.

arguments as __restrict__ (because that's guaranteed by design here) actually
